**Title:** API: which of this node's batches stamp a chunk, or the chunks under a reference

#### Summary

Two read-only endpoints through which a node reports, from its own stamp
issuer's records, which of its batches stamp a chunk:

1. `GET /stamps/{batch_id}/chunks/{address}`: whether this node stamped the
   chunk with this batch, with the stamp's index and timestamp; `404` when
   it did not.
2. `GET /stewardship/{reference}/stamps`: walk the tree as
   `GET /stewardship/{reference}` does and report, for each of the node's
   own batches, how many of the tree's chunks it stamps, and how many
   chunks none of them stamp.

They answer only from the node's own records, about its own batches. Nothing
is asked of other nodes, and the protocol does not change.

#### Motivation

Whoever keeps content alive has to know which of their batches stamp it.
After moving it onto a new batch with `PUT /stewardship/{reference}`, they
also need to know whether all of it moved. Today the node can say only
whether content is retrievable (`GET /stewardship/{reference}`), and that
can't tell the batches apart: while the old batch lasts, a chunk the move
skipped is still retrievable. It shows only when the old batch expires,
which is too late.

So tools keep their own records of what went where, with no way to check
them against the node. Examples are [swarm-keep](https://github.com/petfold/swarm-keep)'s
keep-lists (it checks and moves content onto a new batch before the old one
runs out), Freedom's publish history and the Swarm Desktop File Manager's
drives.

How long a batch lasts stays with the caller. The node already serves what
the estimate needs: the batch's `value` from `GET /batches/{id}`, and
`totalAmount` and `currentPrice` from `GET /chainstate`. So these answers
name batches and nothing about time.

#### Implementation

The node already keeps the record. A stamp issuer stores a
[`postage.StampItem`](https://github.com/ethersphere/bee/blob/v2.8.3/pkg/postage/stampissuer.go#L37-L50)
(batch ID, chunk address, index, timestamp) for every chunk it stamps,
keyed `batchID/chunkAddress`. `stamper.Stamp` reads it so that a chunk
stamped again on the same batch keeps its slot
([`stamper.go` L42–L65](https://github.com/ethersphere/bee/blob/v2.8.3/pkg/postage/stamper.go#L42-L65)).

- (1) is one `Get` of that item.
- (2) is the traversal `GET /stewardship` already does, with one such
  `Get` per chunk for each of the node's usable batches (`/stamps`).

#### Drawbacks

- **Privacy.** A stamp links a chunk to a batch, through the batch to its
  owner's address on chain, and to every other chunk the same batch
  stamped, encrypted ones included.
  - These endpoints answer only the batch's owner, about chunks it stamped
    itself, through its own API, like `/stamps` and `/wallet`. They tell
    no one anything they did not already know.
  - A gateway that stamps uploads for others should keep them closed, as
    it keeps `/stamps` closed.
  - Deliberately not asked:
    - **Stamps in retrieval.** `Delivery.Stamp` has been empty since
      1.17.0. Filling it again would let anyone who downloads content link
      it to its uploader.
    - **Storers telling anyone a chunk's batch or expiry.** An expiry
      alone nearly identifies the batch, and a storer could answer falsely.
- **Cost.** (2) walks the whole tree, as `GET /stewardship` does, so it is
  as slow on a large tree: it fetches every chunk it does not hold. The
  stamp lookups themselves are local.
